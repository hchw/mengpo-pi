# Mengpo Pi · 记忆适配器

把 [Mengpo](https://github.com/hchw/mengpo) 记忆服务接到 [pi](https://github.com/earendil-works/pi) 编码智能体上的扩展，让 pi 在会话中拥有跨会话、可治理、可追溯的长期记忆。

## 背景

pi 每次新会话都从零开始：项目约定、踩过的坑、上次为什么那样改、用户反复纠正过什么——这些经验要么留在人的脑子里，要么散落在仓库与历史会话里，既不会被检索，也不会跨会话累积。

Mengpo 是一个独立的记忆服务：租户级物理隔离、治理状态机、证据与置信度、可解释的混合召回与投影预算。本扩展负责把 pi 接上去。

pi 不是"主流聊天 Agent"，而是编码智能体：它原生带有工具调用标识、会话条目的树形结构、重试与测试结果。因此本扩展以 **Level 2 深度 Runtime Adapter** 的方式接入——不只是旁观消息，而是把「哪次投影、用了哪些记忆、哪次工具调用、哪个结局」串成一条可归因的链路。

## 功能

- **按场景触发召回**：在新用户输入、任务切换、连续失败、用户显式要求回顾时召回并注入；纯工具循环与无新证据的追问则跳过。任务切换以**工作目录变化**识别（可观测、不猜测），显式回顾以**关键词**识别（启发式，误报只多一次召回，深度仍由服务端定）。跳过是为了保住 pi 的提示缓存前缀——每轮注入不同内容会让缓存持续失效，代价高于一次召回往返。判定本身失败时退回"按轮召回"这一安全默认。
- **场景信号上报**：召回时把可观测的场景事实（清晰度、进度、重复失败数、冲突数、证据缺口数）交给服务端，由**服务端**决定专注还是发散；扩展不自行判定发散，因为它看不到全局的冲突与证据缺口。
- **会话活动上报**：工具调用与结果、轮次结局，以显式的来源类别与事件类型上报（失败用 `tool.failure` 表达，而不是把语义塞进载荷字段）。
- **Level 2 运行时 trace**：工具结果标识取自 pi 的 `toolCallId`；顺序取自会话条目在活动分支上的位置，pi 条目标识作为 `source_event_id` 上报、父条目引用记录在事件载荷中（服务端的 `parent_event_id` 是服务端事件引用，不承载 pi 标识）；结局事件额外携带本轮最后一个工具调用标识，使单条事件即可同时具备工具结果与结局标识；投影标识从召回响应回传，由服务端据此派生"实际使用了哪些记忆"。缺失的标识一律省略，不填占位值。
- **记忆工具与人工命令**：`memory_recall` / `memory_remember` / `memory_forget` / `memory_correct` 四个模型可调用工具；`/memory` 查看是否接入、本轮是否注入。
- **反馈回传**：纠正与显式反馈关联到具体记忆；拿不到目标时不上报伪造标识。
- **降级可用**：未配置接入时不发起任何调用；已配置但不可用时静默降级并熔断（连续失败后停止重试）。记忆功能不会阻塞会话，也不会成为延迟来源。

## 使用方法

### 前置依赖

需要 Mengpo 侧的 **`memory-level2-ingress`** 变更**先行发布**：它提供 `observe` 的来源/事件类型/顺序/trace 字段、`project` 的 `projection_id`，以及 `project` 的场景信号入口。

Mengpo 的请求解码为严格模式，未知字段会被拒绝（`INVALID_ENVELOPE`，400），因此**扩展与服务端不能各自独立升级**——先升级服务端。扩展本身对此有降级：被拒绝时会去掉 trace 重报一次，不会让上报链路永久失败。

### 加载

以本地路径加载（不修改任何全局配置）：

```bash
pi -e /path/to/mengpo-pi
```

也可以作为 pi 包安装：`pi install ./mengpo-pi`。扩展入口由 `package.json` 的 `pi.extensions` 声明。

### 配置

| 环境变量 | 说明 |
| --- | --- |
| `MENGPO_PI_BASE_URL` | Mengpo 服务地址，例如 `http://localhost:8080` |
| `MENGPO_PI_ASSERTION` | 会话断言（开发环境即以已验证邮箱作为断言） |
| `MENGPO_PI_TENANT` | 租户标识；省略时自动选择第一个可访问租户 |
| `MENGPO_PI_TIMEOUT_MS` | 单次调用超时，默认 2000，上限 30000 |
| `MENGPO_PI_DEBUG` | 设为 `1` 时把降级原因写到 stderr（凭据始终被脱敏） |

也可以写在 `~/.pi/mengpo.json`：

```json
{
  "baseUrl": "http://localhost:8080",
  "assertion": "dev@mengpo.local",
  "tenantId": "tenant-1234"
}
```

环境变量优先于文件。**两个必填项（地址与断言）任一为空时，扩展完全惰性**：不发起任何调用，也不在每轮重复尝试——那是"未接入"，不是"服务不可用"。

### 运行提示

召回与注入会显式告知用户，便于确认记忆链路是否工作：

```text
mengpo: 记忆获取 3 条 · 触发=新用户输入
mengpo: 记忆注入 3 条
```

触发原因取值：`新用户输入` / `任务切换` / `连续失败` / `显式请求` / `安全默认`。交互模式经 `ctx.ui.notify` 显示，JSON/print 模式改写到 stderr（不污染 stdout）。本轮跳过召回只在 `MENGPO_PI_DEBUG=1` 时输出。

### 命令

```text
/memory          查看接入状态与本轮注入情况
```

## 隐私边界

- 观察默认以**私有可见性**提交，不会默认提升为租户可见。
- 注入的记忆会被标记（`mengpo_injected_memory_ids`），使服务端能区分"模型产生的对话"与"服务端交回的记忆"，避免记忆被再次上报而形成自我引用。
- 是否允许外部 LLM 分析由 **Mengpo 服务端的配置**决定，扩展不会代为放开。
- 凭据不写日志、不进模型可见内容、不进版本库；`MENGPO_PI_DEBUG` 输出也经过脱敏。

## 降级与熔断

记忆是旁路能力，任何失败都退回"无记忆"：

| 情形 | 行为 |
| --- | --- |
| 未配置接入 | 零调用，会话照常 |
| 会话绑定失败 | 会话照常开始，本轮无记忆 |
| 召回超时/失败/空结果 | 提示不变，该轮继续 |
| 服务不可用 | 连续失败达阈值后熔断，冷却期后只放一次探测 |
| 服务端不认识 trace 字段 | 去掉 trace 重报一次 |
